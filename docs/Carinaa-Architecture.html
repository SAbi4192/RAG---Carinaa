Carinaa — RAG Architecture

Every answer, traceable. Two pipelines that share exactly one thing — the vector store. Ingestion runs once per document; query runs once per question. Point at any component to isolate it and watch the data flow along its connections.

Hover any component to trace its connections.

Two pipelines, one shared store

  • Ingestion runs once per document: parse → normalise → chunk → embed → store.
  • Query runs once per question: analyse → embed → search → retrieve → context → generate → cite → ground.
  • They never call each other. The only thing they share is the vector store.
  • So a 300-page PDF is never re-parsed to answer a question, and a bad parse cannot slow down retrieval.

Nothing is hidden behind a framework

  • Every stage writes a TraceEvent with its real duration and real counts.
  • Learning Mode replays the pipeline of the selected answer — each message keeps its own trace.
  • A failed run keeps its trace too, so the interface can name which stage failed.
  • The RAG Laboratory runs the same code as production; it is not a simulation.

Honesty as an architectural constraint

  • Answers come only from retrieved evidence; otherwise the system refuses rather than guessing.
  • Conversation history is context, never document evidence — it can never be cited.
  • Re-ranking and web search report “skipped” when they did not run.
  • A Groq fallback is labelled a fallback; an extractive answer is labelled extractive.
