### Second pass — hover intent-trace

User: *"make it like the factory html … whenever i go to an element it had an
animation."* Reference: `~/Videos/docs/Scarlet-Factory-RAG-Workflow.html`
(archify output, 500 KB).

Reverse-engineered the behaviour from that file rather than guessing:

- CSS in the archify runtime: `svg[data-intent-trace-active] [data-node-id]`
  drops to `opacity:.2`; `[data-intent-trace-match]` returns to 1;
  `[data-intent-trace-selected]` gets `drop-shadow(0 0 10px var(--frontend-stroke))`.
- JS: on `pointerover` of `[data-node-id]`, debounce **90 ms**, then mark the
  node + every edge endpoint it touches, and append an overlay of animated
  `.intent-trace-flow` paths cloned from each edge's own geometry.

Reimplemented in ~70 lines of vanilla JS (no runtime, still one static file).
Rebuilt the SVG so every component is a `<g data-node-id data-node-label>` and
every edge carries `data-edge-from` / `data-edge-to` — that markup contract is
what makes the trace possible. Edges now draw *before* the components so they sit
behind the fills.

Two silent failures hit while testing, both now in the skill:

1. **Listeners were gated behind `(hover: hover) and (pointer: fine)`.** Headless
   reports that as false, so the probe showed `active=none`. Fixed by attaching
   unconditionally and checking `event.pointerType === 'touch'` per event.
2. **A `resize` handler cleared the trace.** Overlay paths are in SVG user units
   so they rescale correctly — the handler was pointless *and* made headless
   screenshots show the un-hovered state (headless fires a resize during initial
   layout, after the synthetic hover). Removed.

Probe method that actually proves it: inject a synthetic
`new PointerEvent('pointerover', {bubbles:true, pointerType:'mouse'})` into a copy,
assert on `--dump-dom` (`matches=7 | flow=3` for a node with 2 out / 1 in), then
screenshot the same copy. Result: hovering *Vector search* dims everything to 16%,
glows that row, and animates flow to *Query embedding*, *Candidate retrieval* and
*ChromaDB*.

Final: `docs/Carinaa-Architecture.html` 41 KB, 32 nodes, 31 edges.

## Backend changes in flight (uncommitted)

Working toward the big "per-message Learning Mode" brief. Backend side done:

- `features/translate.py` — fixed a real **NameError**: `as_list()` was called in
  the unsupported-language branch but never imported. Added `translate_text()`
  for free text (the Learning panel's explanation), which stores nothing — an
  explanation is not a grounded answer and must not become an `AnswerVariant`.
- `api/routes_features.py` — new `POST /features/translate-text`; added
  `_resolve_mode()` so Offline mode refuses instead of silently going online.
- `schemas/chat.py` — `TextTranslateRequest` / `TextTranslateOut`.
- `api/routes_chat.py` — `_question_for()` (resolves the user turn an answer
  belongs to), `_persist_trace()` helper, `question` added to `TraceOut`, and
  `top_sources` (real labels/scores) recorded on the `candidate_retrieval` stage
  so the Learning panel's per-message diagram is built from real evidence.
  A **failed run now persists its trace** against the user message and returns it
  in the error `detail`, so the panel can name the stage that failed instead of
  showing the previous successful pipeline.
- `rag/retriever.py` — removed a duplicated `apply_lexical_blend()` call. It was
  invoked twice in a row and is not idempotent, so the second pass silently
  re-scored every candidate and the trace showed a ranking the first pass did not
  produce. Also removed the duplicated `"lexical_blend": True` dict key.
