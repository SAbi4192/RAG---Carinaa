## Fixed the Vite production build
- **Symptom:** `Rollup failed to resolve import "@/App" from src/main.tsx`, while
  `tsc --noEmit` passed.
- **Cause:** the `@/*` alias exists in `tsconfig.json` `paths` (for the type-checker) but
  Vite/Rollup do **not** read tsconfig, and `vite.config.ts` had no `resolve.alias`.
- **Fix:** added `resolve.alias = { "@": fileURLToPath(new URL("./src", import.meta.url)) }`.
- **Result:** build succeeds, 1873 modules, manual chunks (react/markdown) + per-route
  code splitting working.

## Fixed SPA serving in `backend/app/main.py`
Two real problems with the naive `StaticFiles` mount:
1. The JSON root route at `/` shadowed the landing page.
2. A plain static mount **404s on deep links** (`/dashboard`) because no such file exists
   on disk — that route only exists in React Router.
- **Fix:** `SPAStaticFiles` subclass falling back to `index.html` on 404 (handles both the
  raise and return-404 Starlette behaviours). The JSON root is now registered only when
  there is no frontend build.
- Also added an explicit `/api/{unknown:path}` JSON 404 route so an API typo returns JSON
  instead of HTML (otherwise callers fail with "Unexpected token '<'").

   - Fixed with the real ownership path: trace_events → messages → conversations, filtered

   - **Evidence:** security self-tests went from 5/5 + 1 skipped → **6/6, 0 skipped**.

## Fixed the API-key error + three silent citation/truncation bugs

### The reported error
The user had put their Gemini/Groq keys in `.env.example` (a **template**) and `.env`
did not exist. Created `.env` from the template, restored placeholders in `.env.example`,
added `.gitignore`. Server then logged `gemini=configured groq=configured`.

### Bug 1 — Gemini thinking tokens truncated the answer (root cause of a failing E2E)
`gemini-3.6-flash` charges `thoughtsTokenCount` **against `maxOutputTokens`**. With
`max_tokens=1024`, `thoughts=777` left ~55 tokens, so the answer was cut off mid-sentence
with HTTP 200 and `finishReason=MAX_TOKENS` — no error raised. Symptom looked like a
translation bug: `Translation preserves citations` failed with `original=['1','2']
translated=['2']`.
- Fix: `GEMINI_THINKING_BUDGET` setting (default 0); allowance added **on top** of the
  output budget; `thinkingConfig.thinkingBudget` sent when `>= 0`; `MAX_TOKENS` logged.
- `backend/app/core/config.py`, `backend/app/llm/gemini.py`, `.env.example`.

### Bug 2 — truncation was only detected in the Gemini provider
Groq and llama.cpp report `finish_reason == "length"`, not `MAX_TOKENS`. So a Groq
translation that stopped mid-sentence carried **no warning** and passed validation.
- Fix: `is_truncated()` normaliser + `LLMResponse.truncated` property in
  `backend/app/llm/base.py`; all three providers set `token_usage["truncated"]`.
- `translate.py` now surfaces a visible warning; `shorten.py` treats truncation as a
  **failed validation** (keeps the original).

### Bug 3 — grouped citation markers `[2, 4]` were invisible
`CITATION_RE` was `\[(\d{1,3})\]` — matches `[1]`, not `[2, 4]`. A real answer's
`...scale elastically [2, 4]` resolved to **only citation 1**; citations 2 and 4 never
existed. `validate_translation` had the same blind spot, so a translation could drop a
whole group and still pass.
- Fix: group-aware `CITATION_RE` (`[1-9]` first digit so `arr[0]` can't invent a
  citation) + single authority `iter_citation_numbers()` used by resolution, grounding
  and validation.

### Bug 4 — the Groq fallback cites with full-width brackets `【1】`
U+3010/U+3011. Every regex expected ASCII, so a well-cited Groq answer reported
`citations: 0` and grounding was **falsely** downgraded to PARTIALLY_SUPPORTED. Because
Gemini rate-limits often, this broke citations on exactly the degraded path.
- Fix: `normalize_citation_markers()` — a **fixed translation table**, deliberately NOT
  NFKC (NFKC does not fold U+3010, and it rewrites unrelated user-visible text).
  Applied once at the pipeline boundary, before citation resolution, so the stored
  answer / citations / trace / Read Aloud / validators all agree.
- Also asked the prompt for ASCII brackets explicitly — Groq **still** ignored it, and
  the log recorded `Normalised non-ASCII citation brackets in the generated answer.`
  Lesson: ask the model for a format, never depend on it; validate at the boundary.

## Fixed "Offline Mode is not returning a response" (Phase 2 of the new brief)

### Diagnosis came from the database, not from guessing
The user's complaint was reproduced from stored evidence. `messages` held **13 offline
answers**, all with `provider=local`. Two of them (conv 10) were the user's own test with
**`ADT_Notes.pdf`** (document id 7, 176 chunks):

```
online  (groq)  "Tell me about the PDF" -> detailed, cited answer about the real content
offline (local) "Tell me about the PDF" -> "I could not find this in the documents
                                           in this workspace."
```

There were **no failed offline requests at all** — every attempt returned a response. So
"no response" meant "a refusal", i.e. the user got no *answer*.

### Retrieval was ruled out with numbers
Embeddings and the vector store are local in both modes; only the LLM differs. Top scores:
`0.2749` for the online answer that worked, `0.2887` for the offline refusal. Retrieval was
equally mediocre in both, so the difference had to be the model or the prompt.

### Root cause: one prompt shared by a frontier model and a 3B model
`build_generation_messages` had **no `mode` parameter** — offline and online used the same
2,024-character, six-rule system prompt. Measured with the same chunks
(`scripts/tune_offline_prompt.py`, 5 variants × 2 questions × 3 repeats):

| Prompt | "Tell me about the PDF" | "Who is Donald Triumph?" |
|---|---|---|
| production | REFUSED 3/3 | refused |
| **offline (shipped)** | **answered 3/3** | **refused 3/3** |

Three causes, each confirmed: (1) length — rules steal attention from evidence; (2) the
refusal sentence in the *system* prompt acted as a standing escape hatch (moving it to the
end of the user message as a last resort fixed it — putting it in the system prompt made
refusals **worse**); (3) no licence to summarise, so a broad question read as "context
silent" → refuse.

**Fix:** `OFFLINE_GENERATION_SYSTEM` (198 chars) + mode-specific closing lines in the user
block, selected by a new `mode=` parameter threaded from `pipeline.py`. Online is
byte-identical — asserted by `backend/tests/test_offline_prompt.py` (17 tests).

### Two local-model limits, measured (not bugs to fix)
1. **It never emits EOS for long Indic translations.** Budgets 1024→2048 were all fully
   consumed (`finish=length`), ratio growing linearly 1.72→3.36. So "never truncated" is
   unachievable; the E2E now asserts **disclosure** instead ("A truncated translation is
   disclosed, never silently incomplete"). Do not re-tighten that assertion.
2. **It degenerates into gibberish that passes every check.** With room to ramble it
   produced a 3.8x expansion mixing English into Tamil and looping — yet all citations and
   numbers matched, so the citation/number gates passed. `length_ratio` was already
   computed but **never enforced**. Added `MAX_TRANSLATION_LENGTH_RATIO = 3.0` /
   `MIN_TRANSLATION_LENGTH_RATIO = 0.30` as a degeneration detector (loose on purpose).

Also: translation output budgets are now sized for the **target script** via
`translation_token_budget()` + a `token_expansion` field on `Language` (ta 2.4, ml 2.6,
hi 2.2, ja 1.4, it 0.7) instead of `len(source)//2`, which starved non-Latin scripts.

## RAG "sometimes not working" — duplicate documents were eating top_k

### Root cause found from the user's own workspace (ws 21)
The workspace contained the SAME content three times:
  - id 7  ADT_Notes.pdf  176 chunks / 165,258 chars
  - id 15 ADT_Notes.md   184 chunks / 171,735 chars
  - id 30 ADT_Notes.pdf  176 chunks (a second upload of id 7)
= 536 chunks of effectively one document.

`Retriever._dedupe` used EXACT normalised-text matching (first 400 chars). A PDF
extraction and its Markdown export are the same content but NOT the same string —
converters change whitespace, hyphenation, soft breaks and heading markers — so exact
dedupe missed every one of them. The copies then competed for the same `top_k` slots:
five excerpt slots held ~2 distinct passages, the model saw the same evidence 2-3x,
and the source list showed `ADT_Notes.pdf` and `ADT_Notes.md` as if they were
independent sources. That is why scores looked low (0.17-0.28) and grounding kept
saying PARTIALLY_SUPPORTED.

### Fix — two-pass dedupe (backend/app/rag/retriever.py)
Pass 1: exact normalised text (unchanged).
Pass 2: near-duplicate content, kept if
  jaccard >= 0.82  OR  (containment >= 0.92 AND shared >= 6 words)
The containment term exists because Jaccard penalises SHORT chunks: two header tokens
on a 9-word passage moved it 0.85 -> 0.818 and a real duplicate slipped through.
New setting `retrieval_near_duplicate_threshold` (0.82; 0 disables pass 2 only).
Higher-scoring copy always wins.

### Also
`candidate_k` 20 -> 30. With 536 chunks, 20 candidates sample <4% of the store, so
recall was the limiting factor and re-ranking could not recover a missed passage.

### Proof (live API, 3 copies of one doc = 18 chunks)
  duplicates_removed: 12   (was 0 before — exact matching missed them all)
  returned (top_k):   5    -> 5 DISTINCT passages, each the best-scoring copy
New tests: tests/test_retrieval_dedupe.py (8 tests, both directions).

## Session 3: conversational memory, page-aware retrieval, compact scope UI

### THE USER'S HEADLINE QUESTION: "will it remember my name?"
**Before this session: NO.** Verified by inspection - the pipeline never read
conversation history. Every question was answered from retrieved chunks alone, so
"What is my name?" could not work no matter what.

**Now: YES.** Confirmed with a live test:
  "My name is Abishek and I am working on a RAG project." -> "Nice to meet you, Abishek!"
  "What is my name?"            -> "Your name is Abishek."
  "What topic did I say I was working on?" -> "You said you are working on a RAG project."

Design: retrieval uses the RESOLVED question, generation uses the ORIGINAL plus
history. The conversation goes in its own delimited block labelled "NOT document
evidence, never cite it" - otherwise a small model cites a previous answer as though
it were a PDF passage. History sits ABOVE the excerpts so the excerpts stay nearest
the question.

### PAGE REFERENCES - root cause was NOT missing metadata
`page_number`, `page_end`, `pages` and `section` were ALREADY stored on every chunk.
Nothing ever looked for them. Dense retrieval compares meaning, and "second page" has
no semantic relationship to whatever is written on page 2 - so the constraint had to
become a metadata filter, not a hope about ranking.

- `app/rag/understanding.py`: regex page detection ("page 12", "p.12", "second page",
  "4th page", "page five"). Relative refs ("next page") are DETECTED but deliberately
  NOT resolved - that needs the page the conversation is on, and guessing would be
  worse than reporting the direction.
- `VectorStore._scope_filter` gained `page_number`, matching `page_number` OR
  `page_end` so a chunk spanning pages 2-3 is found by a question about page 3.
- Verified against the user's real PDF: filter=2 returned pages (2,2),(2,3),(1,2);
  filter=11 returned (11,12),(11,11),(10,11); filter=999 returned nothing.
- Page out of range now returns a precise 400 naming the real range, instead of
  running a search that cannot succeed and letting the model invent something.

### FOLLOW-UP DETECTION - the first version was harmful
The initial heuristic flagged "What is a hypervisor?" as a follow-up for being short.
That is the dangerous direction: rewriting a standalone question sends retrieval after
something the user never asked. Rewritten to require an actual anaphoric signal
(pronoun/determiner/elliptical opener), never length alone. Now 9/9 follow-ups true and
6/6 standalone questions false.

## Session 4: relative page references, document disambiguation, and a real bug found

### New: app/rag/references.py
- `resolve_relative_page(direction, history, last_cited_pages)`: turns "the next page"
  into a number using what the conversation established - the most recent page the user
  asked about, else the pages the last answer cited. Returns the REASON alongside the
  number so the trace can show its working. Returns (None, "") when nothing established
  a page: guessing would send retrieval to an invented page.
- `document_mentioned(question, filenames)`: matches the full filename AND the stem,
  case- and separator-insensitive ("adt notes" matches "ADT_Notes.pdf"). People write
  the stem far more often than the extension.
- `needs_document_clarification(...)`: only a PAGE reference triggers this. With 2+
  documents in scope and none named, "page 2" has no single answer, so the request is
  refused with the candidates rather than answered confidently from the wrong document.
  A non-page question ("summarize this document") is deliberately NOT ambiguous -
  summarising both is reasonable, and nagging would be wrong.

### BUG FOUND AND FIXED - and it was mine
A previous patch inserted the module-level `_content_word_set` helper into the MIDDLE
of the `Retriever` class. The next method, `_assert_workspace_has_documents`, was still
indented, so Python parsed it as a NESTED FUNCTION inside `_content_word_set` - after
its `return`, therefore unreachable. `Retriever` lost the method entirely.

Why nothing caught it: the method is only called when retrieval returns ZERO
candidates. Ordinary queries return results and never reach the call. The page filter I
added produces exactly that zero-candidate case, which is how it surfaced - as an HTTP
500 on "tell me about page 2 of alpha_notes".

Two regression tests added:
- assert the methods exist ON the class (`hasattr(Retriever, ...)`), which is the
  distinction that was missed - existing somewhere in the file is not enough
- an AST walk that fails if any `def` is nested inside a module-level function

Lesson worth keeping: when a patch inserts a module-level definition, verify it landed
OUTSIDE the class, not inside it. `ast.parse` succeeds either way.

## Session 8: real-PDF verification - and TWO real bugs it exposed

### The gap, and how it was closed
Every page test so far used Markdown or synthetic data, because the project has no PDF
writer. So page detection -> page filter -> answer had never run end to end against a
real PDF.

PDF is a TEXT format, so `scripts/make_test_pdf.py` writes a valid 4-page PDF by hand
(one distinct chapter per page), then reads it straight back with pypdf to confirm it is
well-formed before anything depends on it.

Worth remembering: the first attempt failed because indirect object numbers were
computed per page instead of reserved up front. Every reference has to be known BEFORE
the object using it is written - pypdf then resolved /F1 to a content stream and raised
KeyError '/DescendantFonts'.

### BUG 1 - `_page_range` ignored `page_end`
A short document becomes ONE chunk covering all its pages: `page_number: 1,
page_end: 4`. `_page_range` read `page_number` for BOTH bounds, so a four-page document
reported **"pages 1 to 1"** and rejected every page question as out of range.
Fix: `min(page_number)` .. `max(page_end)`.

### BUG 2 - the page filter missed chunks that span the page
The filter was `page_number == N OR page_end == N`. The chunk above satisfies that for
page 1 and page 4 but NOT page 2 - so page 2 of a four-page document found nothing even
though the chunk contains page 2. Fix: a range test,
`page_number <= N AND page_end >= N`.

Both were invisible to every existing test. The range bug needed a real PDF to appear;
the filter bug needed a chunk that spans pages, which only short documents produce.

### A limitation worth stating, not hiding
With the fixes, a page question on the 4-page test PDF now finds the chunk and applies
the filter - but the model still refuses, because ONE chunk covering pages 1-4 cannot be
narrowed to page 2 by any filter. That is a chunking limit, not a retrieval bug: the
user's real ADT_Notes.pdf has 176 chunks across its pages, so page-aligned retrieval
works properly there. A short document simply cannot be more precise than its chunking
allows.

### Tests
61 in test_conversational_rag.py (was 58): the spanning-chunk filter, the workspace
condition surviving the range test, and a guard that `_page_range` reads `page_end`.
One OLDER test asserted the previous equality shape and was updated - the behaviour
changed deliberately, so the test had to change with it.

## Session 10: unit references, and a bug class I introduced twice

### The reported failure, diagnosed properly
The brief reported that on a real document:
  "What is the name of UNIT III?"   -> worked
  "What does the third unit say?"   -> "Not enough evidence"
  "Summarise Unit III"              -> sometimes the wrong section

Inspecting the actual metadata showed the cause is NOT a threshold and NOT weak
retrieval. The document has sections for UNIT I, IV and V and NONE for II or III, so
there was nothing to filter on. And more fundamentally: **"third" and "III" are the same
concept in two alphabets, and nothing connected them.** The body contains the literal
string "UNIT III", so a question saying "UNIT III" matches it; a question saying "third
unit" shares no tokens at all, and an embedding cannot bridge an ordinal to a Roman
numeral - that is a transformation, not a similarity.

### Fix: app/rag/units.py
`detect_unit_reference` understands Roman ("unit III"), Arabic ("unit 4") and word
("third unit", "unit five") forms across unit/module/chapter/part/section, and returns
the canonical Roman form. `expand_unit_reference` APPENDS it to the query rather than
substituting, so the user's own wording still drives the semantic search and the token
the document actually uses is added alongside.

Expansion rather than a metadata filter, because section metadata is only as complete as
the document's headings - filtering on "UNIT III" would find nothing on a document whose
headings skip it, while searching the content works regardless.

Verified end to end on a purpose-built 5-page PDF with UNIT I..V headings:
  "What does the third unit say?" -> "UNIT III - Concept Generation" (correct)
  "Tell me about page 3"          -> page filter applied, page 3 content
  "Summarise Unit III"            -> correct

### BUG - and it is a class I hit TWICE
Trace annotations written BEFORE retrieval silently did nothing. `query_analysis` is
recorded DURING retrieval, so at annotation time the event did not exist, the loop found
nothing, and the note was dropped with no error at all.

It hit the unit note first, then - after I fixed only that one - the follow-up
`resolved_question`, which still showed as None while the answer was right. Both are now
applied together after the run.

Lesson: when annotating a trace, confirm the event exists at the point of writing. A
loop over `trace.events` that matches nothing is silent by construction.

Also fixed: `is_followup` was only recorded when the rewrite CHANGED the question. "What
is my name?" is self-contained as a string, so the model leaves it unchanged and the
trace showed nothing - even though the conversation was what made it answerable.
Detection and rewriting are now recorded as separate facts.
